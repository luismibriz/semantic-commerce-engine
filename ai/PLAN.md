# PLAN — Semantic Discovery Engine

Functional and technical specification. It is written to be executable by an
AI agent: it states *what* to build and the constraints it must not break,
without ambiguity.

---

## 1. Problem and business rules

An online sports retailer sells cycling and fitness products. Keyword search
fails shoppers who describe an *intent* ("camiseta roja para el frío") rather
than exact product words. This engine matches intent to products using vector
embeddings.

Business rules:

- **BR-1** A product is *discoverable* only after it has been indexed (an
  embedding has been generated for it).
- **BR-2** Indexing is idempotent per product identity: re-indexing the same
  product id updates its catalog data and refreshes its embedding; it never
  creates a duplicate.
- **BR-3** Changing a product's catalog data (name, description, price)
  invalidates its embedding — the product is stale until re-indexed, because
  the searchable text changed.
- **BR-4** The embedding used to index a product and the embedding used for a
  query MUST come from the same model and dimensionality, or similarity is
  meaningless.
- **BR-5** Search returns products ordered by descending semantic relevance.
  Relevance is the cosine similarity of the embeddings.
- **BR-6** A search request is bounded: it returns between 1 and 50 results
  (default 10). The catalog is never scanned unboundedly.
- **BR-7** Money is always an exact integer amount of minor units with an
  ISO-4217 currency. Floating point is forbidden for money.

## 2. Domain model

Bounded context: **Catalog** (product catalog + discovery).

### Aggregate: `Product` (aggregate root)

State: `ProductId`, `ProductName`, `ProductDescription`, `Money` price,
optional `EmbeddingVector`, optional `indexedAt` timestamp.

Behaviour:

- `register(id, name, description, price)` — create a non-indexed product.
- `reviseCatalogData(name, description, price)` — update catalog data; clears
  the embedding (BR-3).
- `index(embedding, occurredOn)` — attach the embedding, mark indexed, record
  a `ProductWasIndexed` event.
- `searchableText()` — the exact text fed to the embedding model (BR-4).
- `isIndexed()`, `releaseEvents()`.

### Value objects

- `ProductId` — UUID, generated by the client (no DB round-trip on the write
  path).
- `ProductName` — non-empty, ≤ 150 chars.
- `ProductDescription` — non-empty, ≤ 5000 chars. Main semantic signal.
- `Money` — `amount` (int, minor units, ≥ 0) + `currency` (ISO-4217). Rejects
  floats and negative amounts; arithmetic only between equal currencies.
- `EmbeddingVector` — immutable list of finite floats. Knows its dimension and
  computes cosine similarity. Treated as an opaque value by the domain.
- `SearchQuery` — non-empty trimmed text, ≤ 500 chars.
- `SearchLimit` — integer in [1, 50], default 10 (BR-6).
- `RelevanceScore` — cosine similarity in [-1, 1].
- `ProductMatch` / `SearchResults` — read model; `SearchResults` enforces the
  descending-relevance invariant on construction (BR-5).

### Domain event

- `ProductWasIndexed(productId, dimensions, occurredOn)` — drives the read
  model projection.

### Ports (interfaces owned by the domain)

- `ProductRepository` — write-model persistence (`ofId`, `save`, `all`).
- `EmbeddingGenerator` — turns text into an `EmbeddingVector` (external model).
- `Clock` — supplies "now" deterministically.
- `SemanticProductSearch` — read side: rank products for a query vector.
- `ProductSearchIndex` — projection side: upsert/remove a product in the
  search store.

## 3. Use cases

### UC-1 — Index a product (command, write side)

`IndexProductCommand(productId, name, description, priceAmount, priceCurrency)`
→ `IndexProductHandler`.

Flow:
1. Build value objects (validation happens here).
2. Load the product by id; if absent, `register`; if present,
   `reviseCatalogData` (BR-2).
3. Generate the embedding from `searchableText()` **before persisting** — a
   failing provider aborts the use case cleanly.
4. `index()` the product with the embedding and `Clock::now()`.
5. `save()` the product.
6. Publish the recorded `ProductWasIndexed` event.

Happy path: product is stored in Postgres with its embedding; the event
triggers a projection into Elasticsearch.

Sad paths:
- Empty/oversized name or description → `InvalidArgument` (400).
- Negative price or non-ISO currency → `InvalidArgument` (400).
- Malformed product id → `InvalidArgument` (400).
- Embedding provider down → `EmbeddingFailed` (502); nothing is persisted.

### UC-2 — Search products (query, read side)

`SearchProductsQuery(text, limit?)` → `SearchProductsHandler`.

Flow:
1. Build `SearchQuery` and `SearchLimit` (validation).
2. Embed the query text with the same `EmbeddingGenerator`.
3. Ask `SemanticProductSearch` for the most relevant products.
4. Return a `SearchProductsResponse` read model.

Happy path: products ranked by descending cosine similarity, capped at the
limit.

Sad paths:
- Empty query → `InvalidArgument` (400).
- `limit` outside [1, 50] → `InvalidArgument` (400).
- No products indexed → empty result list, HTTP 200.

### UC-3 — Remove a product (command, write side)

`RemoveProductCommand(productId)` → `RemoveProductHandler`.

Flow:
1. Load the product by id.
2. `remove()` the aggregate, which records a `ProductWasRemoved` event.
3. Delete it from the repository.
4. Publish the event — a projector then evicts it from the search read model.

It is symmetric with UC-1: the handler touches only the write model and never
the read store.

Happy path: the product is gone from PostgreSQL and from search; HTTP 204.

Sad path: unknown id → `ProductNotFound` (404).

### UC-4 — Rebuild the read model (maintenance)

`search:reindex` console command resets the search index (Elasticsearch or
pgvector) and re-projects every indexed product from PostgreSQL. Proves the
read store is fully derivable from the source of truth.

## 4. Architecture decisions the agent MUST respect

- **AD-1 Hexagonal layering.** `Domain` and `Application` contain zero
  framework imports. All Symfony/Doctrine/Elasticsearch code lives in
  `Infrastructure`. Dependencies point inwards.
- **AD-2 CQRS with a separate read store.** Postgres is the write model and
  single source of truth. Elasticsearch is a derived read model for search.
  Three Messenger buses: `command.bus`, `query.bus`, `event.bus`.
- **AD-3 Projection via domain event.** `IndexProductHandler` does not know the
  read store exists. `ProductWasIndexed` is handled by a projector that writes
  to Elasticsearch.
- **AD-4 Pure entity + XML mapping.** `Product` carries no ORM metadata;
  Doctrine maps it through `config/doctrine/*.orm.xml` and custom DBAL types.
- **AD-5 Embedding behind a port.** `EmbeddingGenerator` is an interface.
  Adapters: `OpenAiEmbeddingGenerator` (production) and
  `HashingEmbeddingGenerator` (offline, deterministic — for tests and for
  running the stack without an API key).
- **AD-6 Pluggable vector store.** The read side is reached through the
  `SemanticProductSearch` and `ProductSearchIndex` ports. Two adapters are
  interchangeable via `SEARCH_BACKEND`: Elasticsearch (`dense_vector` +
  `knn`, default) and PostgreSQL `pgvector` (`vector` column + HNSW). The
  domain, the use cases and the tests are identical for both.

## 5. Technical constraints (anti-patterns to avoid)

- Do NOT put validation in controllers — value objects validate.
- Do NOT return entities from query handlers — return read-model DTOs.
- Do NOT let commands return data — the write side is fire-and-forget.
- Do NOT store money as a float anywhere.
- Do NOT generate embeddings lazily at search time for products — index time
  only; search embeds the query once.
- Do NOT scan the whole catalog in PHP to rank — ranking happens in
  Elasticsearch (or, in tests, in the in-memory double).
- Do NOT add a generic `AbstractRepository`/`BaseEntity` — keep the model
  specific to this context.

---

## 6. Performance

- Indexing cost = 1 embedding API call + 1 Postgres write + 1 Elasticsearch
  upsert. Embeddings are computed once, at index time.
- Search cost = 1 embedding API call + 1 Elasticsearch `knn` query. The
  `dense_vector` field is indexed (HNSW), so search is approximate-nearest-
  neighbour, sub-linear in catalog size — not a full scan.
- `num_candidates` is `max(100, 10 × limit)`: the recall/latency knob.
- See `README.md` § Performance for the measured numbers.

---

## 7. Out of scope

Authentication, product images, inventory/stock, multi-language embeddings,
re-ranking models, pagination cursors. This is a focused discovery engine,
not a full catalog service.
